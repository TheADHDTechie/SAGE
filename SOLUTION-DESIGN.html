SAL WhatsApp Support Assistant - Solution Design

Status: Implemented and verified prototype
Date: September 16, 2026
Audience: SAL product, program, engineering, safeguarding, and operations teams

1. Executive summary

This document describes an initial support assistant for Start A Library Trust (SAL). End users ask questions through WhatsApp using text or voice messages. The assistant answers from the SAL Teacher Librarian Guide, responds in English or Kiswahili, cites the relevant manual pages, and transfers unsupported or sensitive requests to a human. Voice questions can receive WhatsApp voice-note answers generated by Azure Speech, with citations sent separately as text.

The initial prototype uses:

  • Meta WhatsApp Cloud API for messaging.
  • Interactive WhatsApp lists and typed commands for reply-format preferences.
  • A Node.js and TypeScript API service.
  • Azure Container Apps with one always-running replica and managed identity.
  • GPT-5.6 Luna deployed in Microsoft Foundry for language understanding and grounded answer generation.
  • Azure Speech fast transcription with English and Kiswahili candidate locales.
  • Azure neural text-to-speech with Kenyan English and Kiswahili voices.
  • The complete processed manual supplied to the LLM on each request.
  • Container-local SQLite storage for conversations, reply preferences, idempotent delivery plans, handoffs, and audit events.
  • The existing knowledge-base\sal\data\sal-guide-chunks.jsonl file as the authoritative knowledge source.

The prototype deliberately avoids an agent framework, embedding service, vector database, and distributed job infrastructure. The manual is small enough to fit in the model context, and expected initial traffic is low. Components are isolated behind interfaces so local hybrid retrieval can be added later without changing WhatsApp or conversation behavior.

2. Goals

The prototype must:

  1. Receive WhatsApp text, voice, and interactive-list messages.
  2. Answer questions using only the approved SAL manual.
  3. Support English, Kiswahili, and mixed-language enquiries.
  4. Respond in the user's language using text, voice, or both according to preference.
  5. Cite the manual chapter and PDF page range for factual answers.
  6. Refuse to invent answers when the manual is insufficient.
  7. Transfer conversations to a human when requested or required.
  8. Apply deterministic safeguarding and emergency routing rules.
  9. Keep the manual, conversation history, identifiers, and operational data local to the API service.
  10. Keep the Azure model deployment replaceable through configuration.
  11. Persist multi-step outbound delivery state so partial Meta failures can be retried without regenerating the answer or re-uploading completed audio.

3. Constraints and assumptions

  • The prototype uses the processed 44-page SAL Teacher Librarian Guide knowledge bundle with 57 semantic sections and 58 chunks; five image-transcribed appendix chunks require final human proofing.
  • Initial user volume is low enough that one Azure generation call per normal message is acceptable.
  • The current Azure Container App uses ephemeral container-local SQLite at /tmp/sage-data; state is reset when a new revision replaces the replica.
  • The deployment is intentionally limited to one replica because sender serialization and SQLite delivery claims are process-local.
  • The public deployment provides HTTPS endpoints reachable by Meta webhooks.
  • Human handoff currently pauses bot replies and exposes a protected staff reset API. Staff-message echo handling through WhatsApp Business App Coexistence and a full staff inbox remain future production work.

4. Key architecture decisions

4.1 Use full-manual context for the MVP

The API sends all 58 structured manual chunks to GPT-5.6 Luna with each user question. This avoids retrieval misses and removes the need for embeddings, a vector index, query rewriting, and reranking.

The API preserves chunk boundaries and metadata:

<manual_chunk
  id="sal-0423ac330bdd"
  title="Setting Up a Child-Friendly Library Space"
  chapter="Chapter 2: Practical School Library Operations"
  pages="8-9"
  language="en"
>
...
</manual_chunk>

This is preferred for the prototype because the corpus is small, implementation is simple, and the absolute model cost remains low at the expected volume.

4.2 Use deterministic orchestration rather than an agent

Application code controls every step. The LLM cannot decide to call arbitrary tools, send messages, access files, or update state.

Receive message
-> validate and deduplicate
-> apply routing rules
-> apply deterministic preference commands or interactive selections
-> transcribe when needed
-> construct grounded prompt
-> invoke Azure LLM
-> validate structured result
-> resolve text, voice, or both output
-> synthesize and upload audio when required
-> execute a persisted multi-step delivery plan
-> send answer or create handoff

This provides predictable behavior, simpler testing, explicit failure handling, and a clear audit trail.

4.3 Keep business data local to the API service

The complete manual, WhatsApp identifiers, message history, staff notes, feedback, and audit records remain in local files or SQLite. Azure receives only the minimum context required to process the current request.

4.4 Use user-controlled multimodal replies

Each contact has a deterministic reply preference:

  • auto: text questions receive text; voice questions receive voice plus text sources.
  • text: all supported answers are sent as complete text with sources.
  • voice: answers are spoken, with sources retained as a short text message.
  • both: the spoken answer and complete text answer are both sent.

New contacts default to auto. After the first successful automatic voice reply, SAGE sends a WhatsApp interactive list once. Users can reopen it with SETTINGS or MIPANGILIO, and typed commands remain available if interactive delivery fails.

Preference parsing occurs before the LLM. Preferences change only output format; safeguarding, explicit human requests, grounding, citations, and handoff policy retain priority.

4.5 Persist outbound delivery as ordered steps

A response can contain several outbound messages: audio, sources, full text, and a preference list. Before delivery, SAGE stores an ordered JSON delivery plan in SQLite. Each completed step stores its Meta message ID. A retry therefore resumes from the first incomplete step instead of regenerating the model answer, synthesizing the audio again, or resending already checkpointed steps.

5. High-level architecture

6. Component design

6.1 WhatsApp adapter

Responsibilities:

  • Verify webhook subscription challenges.
  • Validate incoming webhook authenticity according to Meta requirements.
  • Parse text, audio, interactive list selections, contact, and message identifiers.
  • Deduplicate incoming message IDs.
  • Retrieve voice-media metadata and download audio using authorized Meta endpoints.
  • Upload synthesized OGG/Opus audio.
  • Send text, voice-note, and interactive-list responses.
  • Record delivery and failure status updates.

The adapter exposes provider-neutral application types:

interface IncomingSupportMessage {
  providerMessageId: string;
  contactId: string;
  type: "text" | "voice";
  text?: string;
  mediaId?: string;
  receivedAt: string;
}

interface MessagingProvider {
  downloadAudio(mediaId: string): Promise<DownloadedAudio>;
  uploadAudio(audio: SynthesizedAudio): Promise<{ mediaId: string }>;
  sendText(contactId: string, text: string): Promise<SentMessage>;
  sendAudio(contactId: string, mediaId: string): Promise<SentMessage>;
  sendList(contactId: string, list: InteractiveList): Promise<SentMessage>;
}

6.2 Conversation service

Responsibilities:

  • Find or create the active conversation.
  • Maintain bot, waiting_for_human, human, and closed states.
  • Load a limited number of recent messages.
  • Pause automated replies while a human owns the conversation.
  • Store inbound, generated, and staff messages.
  • Store model results, citations, feedback, and failure reasons.
  • Store auto, text, voice, or both reply preferences per contact.
  • Store whether the initial voice-preference prompt has already been shown.
  • Store ordered outbound delivery steps and completed Meta message IDs.

6.3 Rules and policy router

Rules run before the LLM and take precedence over generated output.

Initial deterministic rules:

  • Explicit request for a human.
  • Stop or opt-out request.
  • Conversation already assigned to a human.
  • Empty or unsupported media.
  • Greeting and thanks responses that do not require the manual or an LLM call.
  • Reply-preference commands and interactive selections.
  • Audio exceeding configured duration or size.
  • Repeated processing of the same provider message ID.
  • Approved safeguarding and emergency keywords or flows.

The LLM may recommend handoff, but only the application changes conversation state.

6.4 Speech transcription service

The implemented service uses the Azure Speech fast-transcription REST API with en-US and sw-KE candidate locales. WhatsApp OGG/Opus and other supported formats are converted to 16 kHz mono PCM WAV with FFmpeg before transcription.

Responsibilities:

  • Validate MIME type, size, and configured duration.
  • Save audio under a random temporary filename.
  • Transcribe English, Kiswahili, or mixed-language speech.
  • Return transcript text and detected language when available.
  • Delete the temporary recording after processing.
  • Reject empty or unusable transcripts.
interface SpeechTranscriber {
  transcribe(input: {
    bytes: Uint8Array;
    mimeType: string;
  }): Promise<{
    text: string;
    locale?: string;
  }>;
}

For safeguarding concerns, names, dates, phone numbers, or other consequential details, the assistant asks the user to confirm the transcript before relying on it.

6.5 Speech synthesis service

When the resolved reply mode includes voice, the API sends the validated answer text to Azure neural text-to-speech.

Implemented voices:

  • English: en-KE-AsiliaNeural
  • Kiswahili: sw-KE-ZuriNeural

The service requests ogg-24khz-16bit-mono-opus, which can be uploaded directly to Meta and sent with audio.voice=true. Citations are not spoken; they remain a separate text message. Long answers are shortened for speech and the complete answer is sent as text.

Authentication uses the Container App managed identity and the Azure Speech resource ID. No Speech API key is stored in the deployed Container App.

interface SpeechSynthesizer {
  synthesize(input: {
    text: string;
    language: SupportedLanguage;
  }): Promise<{
    bytes: Uint8Array;
    mimeType: "audio/ogg";
    fileName: string;
  }>;
}

6.6 Reply preference and interactive-message service

Preference selections use namespaced identifiers such as:

preference:en:auto
preference:en:text
preference:en:voice
preference:en:both

This format keeps preference handling deterministic and leaves room for future interactive surveys, for example survey:library-profile:q1:yes, without coupling survey logic to the LLM.

The interactive list is offered once after the first successful automatic voice reply. SETTINGS, MIPANGILIO, and typed preference commands reopen or update the selection. If Meta rejects the list, SAGE sends typed choices instead.

6.7 Knowledge repository

The authoritative source is:

knowledge-base\sal\data\sal-guide-chunks.jsonl

The service loads and validates this file at startup. Every record must contain:

  • id
  • title
  • chapter
  • section
  • topic
  • tags
  • content_type
  • language
  • page_start
  • page_end
  • text

Startup must fail visibly if:

  • the file is missing;
  • a JSON line is invalid;
  • chunk IDs are duplicated;
  • required metadata is absent;
  • a page range is invalid.

The repository creates a stable, bounded manual-context string once at startup and reuses it for requests.

6.8 LLM gateway

The LLM gateway hides Azure SDK and deployment details:

interface LanguageModelGateway {
  answerSupportQuestion(input: {
    question: string;
    inputLanguage?: string;
    recentMessages: ChatMessage[];
    manualContext: string;
  }): Promise<SupportModelResult>;
}

Configuration:

AZURE_AI_ENDPOINT=
AZURE_AI_API_KEY=
AZURE_LLM_DEPLOYMENT=gpt-5.6-luna
AZURE_LLM_REASONING_EFFORT=low
AZURE_LLM_MAX_OUTPUT_TOKENS=600

The implementation uses an Azure SDK supported by the selected deployment. No model-specific behavior should leak into the conversation or WhatsApp adapters.

6.9 Prompt builder

The prompt contains:

  1. SAL assistant role and scope.
  2. Safeguarding and refusal instructions.
  3. Response-language instructions.
  4. Recent conversation messages.
  5. All structured manual chunks.
  6. The current user message or voice transcript.
  7. A strict structured-output schema.

Core instructions:

- Answer only from the supplied manual chunks.
- Respond in the user's language.
- Keep the answer concise and suitable for WhatsApp.
- Preserve names, numbers, schedules, requirements, and procedures exactly.
- Cite only chunk IDs included in the supplied manual.
- If the manual is insufficient, set supported=false.
- Do not make safeguarding, eligibility, legal, medical, or financial decisions.
- Recommend human handoff when the request requires individual judgment.

6.10 Response validator

Expected model output:

interface SupportModelResult {
  language: "en" | "sw" | "mixed" | "unknown";
  answer: string;
  supported: boolean;
  citedChunkIds: string[];
  requiresHuman: boolean;
  handoffReason?: string;
}

Local validation must confirm:

  • The response matches the schema.
  • Every cited chunk ID exists.
  • Supported factual answers include at least one citation.
  • The answer length is within the configured limit.
  • Unsupported answers do not present manual-derived claims as confirmed facts.
  • Human handoff is created when requiresHuman is true.

If validation fails, the service sends a safe fallback and records the model response for engineering review. It does not send malformed or ungrounded content.

6.11 Human handoff channel

The implemented prototype creates a handoff, sends an approved notice, and suppresses further bot responses while the conversation is waiting for or owned by staff. A protected staff endpoint can return a contact to chatbot control.

WhatsApp Business App Coexistence is a planned staff-channel option, not a completed part of the current prototype.

With Coexistence, the same SAL business number is connected to:

WhatsApp Business app used by SAL staff
                    +
WhatsApp Cloud API used by the assistant

The required flow is:

Bot determines that handoff is required
-> API changes conversation status to waiting_for_human
-> user receives an approved handoff message
-> staff sees and answers the conversation in WhatsApp Business
-> API receives the staff-message echo
-> conversation status changes to human
-> automated replies remain paused

The application must subscribe to and process the relevant message-echo webhook so it can distinguish staff messages from bot-generated outbound messages. While a conversation is in waiting_for_human or human state, incoming user messages are stored but are not sent to the LLM.

This option requires:

  • A SAL phone number registered with the WhatsApp Business app.
  • Eligibility and enablement for WhatsApp Business App Coexistence.
  • Successful connection of that number to the Cloud API.
  • A tested staff-message echo flow.

Coexistence must be confirmed before changing or migrating SAL's active support number. The team should test onboarding and handoff with a separate number first.

If SAL has no Coexistence-enabled number, staff cannot use the same WhatsApp Business app conversation as the Cloud API assistant. In that case, the solution must include a protected custom staff chat interface that sends staff replies through the Cloud API.

6.12 Custom staff chat interface

This component is required only when Coexistence is unavailable, or later when SAL needs stronger assignment, reporting, and multi-agent capabilities.

The minimal staff interface supports:

  • Listing conversations waiting for a human.
  • Viewing recent messages, transcript, generated answer, and cited chunks.
  • Claiming a conversation.
  • Sending a manual WhatsApp reply.
  • Returning a conversation to bot mode.
  • Closing a conversation.
  • Marking an answer correct, incorrect, or requiring review.

Authentication can use one simple deployment-appropriate mechanism for the prototype, but the inbox must not be publicly accessible.

9. Security, privacy, and safeguarding

9.1 Data minimization

Send Azure only:

  • the current question or transcript;
  • a small recent conversation window;
  • the approved manual chunks;
  • response instructions.

Do not send:

  • WhatsApp phone numbers;
  • internal staff notes;
  • authentication data;
  • complete user profiles;
  • unrelated conversation history.

9.2 Audio handling

  • Validate media type and configured size.
  • Use random temporary filenames.
  • Do not log audio bytes or signed download URLs.
  • Delete temporary files after transcription, including failure paths.
  • Retain recordings only if SAL defines a justified and approved policy.
  • Keep synthesized audio in memory only until it is uploaded to Meta.
  • Store only Meta's media ID in the delivery plan, not the generated audio bytes.
  • Do not speak citations, phone numbers, or internal metadata unless they are part of the validated answer.

9.3 Secrets

  • Load Azure and Meta credentials from the deployment secret store.
  • Never store credentials in source code, SQLite, or logs.
  • Rotate secrets according to organizational policy.
  • Use the minimum required permissions.

9.4 Safeguarding

Safeguarding responses are approved by SAL and implemented as deterministic policy. The model can classify or recommend escalation, but it cannot investigate allegations, promise confidentiality, or decide whether a report is valid.

The five image-transcribed appendix records must receive human verification before they are used in a production safeguarding response.

10. Reliability and failure handling

10.1 Idempotency

provider_message_id is unique. Receiving the same webhook more than once must not produce duplicate model calls. Multi-step deliveries checkpoint each accepted Meta message ID and resume from the first incomplete step. This avoids re-synthesizing or re-uploading audio and avoids resending previously checkpointed steps.

As with most external messaging APIs, there remains a narrow at-least-once window if Meta accepts a message but the process stops before SQLite records the returned message ID. Production hardening should reconcile outbound status webhooks before retrying an uncertain step.

10.2 Timeouts and retries

  • Acknowledge the WhatsApp webhook promptly.
  • Store work before starting Azure inference.
  • Retry transient Azure and Meta failures with bounded exponential backoff.
  • Do not retry invalid requests or permanent authorization failures.
  • Never report success until the outbound message is accepted.

For the earliest demo, processing may happen in the request path. Before external testing, use a durable SQLite-backed work queue so webhook handling is not coupled to model latency.

10.3 Safe fallback

When transcription, inference, validation, or outbound delivery fails:

  1. Record the failure without sensitive prompt content.
  2. Avoid sending a success-shaped answer.
  3. Retry only when the failure is transient.
  4. Transfer to staff or send an approved temporary-failure response.

11. Observability

Record:

  • inbound message count by text or voice;
  • processing latency by stage;
  • Azure transcription and generation latency;
  • Azure text-to-speech latency and generated audio size;
  • Azure token usage when returned;
  • supported versus unsupported answers;
  • handoff count and reason;
  • citation-validation failures;
  • duplicate webhook count;
  • outbound delivery failures;
  • interactive-list delivery failures and typed-choice fallbacks;
  • reply-mode distribution;
  • staff feedback and correction rate.

Logs should use generated contact and conversation IDs rather than phone numbers. Prompt and transcript logging is disabled by default.

12. Cost model

The primary variable costs are:

  • GPT-5.6 Luna input and output tokens.
  • Azure speech transcription for voice messages.
  • Azure neural text-to-speech for voice replies.
  • Meta media upload and additional source/preference messages.
  • WhatsApp messaging charges.
  • Hosting and persistent storage.

Using an illustrative 15,000 input tokens and 250 output tokens per full-manual request, the previously assessed Luna model cost is approximately:

Answers Approximate LLM cost
100 $0.33
1,000 $3.30
10,000 $33.00

These are planning estimates, not billing guarantees. Confirm prices for the selected Azure region, deployment type, currency, and agreement before launch. Track actual token usage from the first demo.

Prompt caching may lower repeated manual-input cost, but the business case must not depend on cache eligibility.

13. Quality and acceptance criteria

Create a reviewed evaluation set of at least 50 questions:

  • direct English questions;
  • paraphrased English questions;
  • Kiswahili questions;
  • English/Kiswahili code-switching;
  • vague conversational follow-ups;
  • questions requiring more than one section;
  • questions not answered by the manual;
  • safeguarding and human-handoff cases;
  • clear and noisy voice recordings.

Prototype acceptance targets:

15. Evolution to local hybrid retrieval

Add retrieval when:

  • the number of manuals grows;
  • full-context latency becomes unacceptable;
  • traffic makes repeated full-context input materially expensive;
  • evaluation reveals attention or section-selection failures;
  • different audiences need filtered knowledge.

Target future flow:

Question
-> optional English query normalization
-> local keyword and vector search
-> reciprocal-rank fusion
-> best 5-8 chunks
-> GPT-5.6 Luna
-> local citation validation

Potential future components:

  • Cohere Embed 4 deployed through Microsoft Foundry.
  • Local embedded LanceDB.
  • Full-text and vector hybrid search.
  • Reciprocal Rank Fusion.
  • Optional reranking only if measured retrieval quality requires it.

The LanguageModelGateway, KnowledgeRepository, and processMessage interfaces should prevent this migration from affecting WhatsApp, staff handoff, or persistence.
